# 事务管理机制

事务是逻辑上的一组操作，要么全执行，要么全不执行。

## 事务的四大特性

事务的定义很严格，它必须同时满足四个特性，即`原子性`、`一致性`、`隔离性`和`持久性`，也就是ACID 特性，具体如下：

| 特性   | 描述                                                         |
| ------ | ------------------------------------------------------------ |
| 原子性 | 事务是一个原子操作单元，对数据的修改要么全部执行，要么全部不执行 |
| 一致性 | 事务在开始和完成时，数据必须保持一致状态                     |
| 隔离性 | 事务之间应该隔离开来，使每个并发中的事务不会互相干扰         |
| 持久性 | 事务完成后，对数据的修改是永久的，即使系统发生故障也能保持   |

## 事务并发带来的问题

数据库并发操作可能带来的`脏读`、`不可重复读`、`幻读`和`丢失更新`等问题，具体如下：

| 问题       | 描述                                                         |
| ---------- | ------------------------------------------------------------ |
| 脏读       | 一个事务读取到另一个事务未提交的数据                         |
| 不可重复读 | 一个事务对同一行数据重复读取两次，但得到的结果不同           |
| 幻读       | 一个事务执行两次查询，但第二次查询的结果包含了第一次查询中未出现的数据 |
| 丢失更新   | 多个事务同时更新一行数据，后提交（或撤销）的事务将之前事务提交的数据覆盖了 |

## 隔离级别

为了避免上述事务并发问题的出现，在标准的 SQL 规范中定义了四种事务隔离级别，不同的隔离级别对事务的处理有所不同。这四种事务的隔离级别如下：

| 隔离级别                  | 描述                                                         | 脏读   | 不可重复读 | 幻读   |
| ------------------------- | ------------------------------------------------------------ | ------ | ---------- | ------ |
| 读未提交 Read Uncommitted | 事务可以读取其他事务尚未提交的更改（“脏数据”）               | 可能   | 可能       | 可能   |
| 读已提交 Read Committed   | 事务只能读取其他事务已提交的数据                             | 不可能 | 可能       | 可能   |
| 可重复读 Repeatable Read  | 事务内多次读取同一数据的结果一致，不可以读取其他事务已提交的数据 | 不可能 | 不可能     | 可能   |
| 串行化 Serializable       | 事务完全串行执行                                             | 不可能 | 不可能     | 不可能 |

一般来说，事务的隔离级别越高，越能保证数据库的完整性和一致性，但相对来说，隔离级别越高，对并发性能的影响也越大。因此，通常将数据库的隔离级别设置为`读已提交`，它既能防止脏读，又能有较好的并发性能。虽然这种隔离级别会导致不可重复读、幻读和第二类丢失更新这些并发问题，但可通过在应用程序中采用悲观锁和乐观锁加以控制。
