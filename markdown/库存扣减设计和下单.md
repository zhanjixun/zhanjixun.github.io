# 库存扣减设计和下单

在 Java 业务系统中，库存扣减与下单逻辑是电商系统的核心。设计一个高并发、高可用且数据一致的库存系统，通常需要根据业务规模从**数据库事务**、**分布式锁**到**缓存预扣减**逐步演进。

以下是三种常见的设计方案及其深度解析：

------

## 方案一：数据库行级锁（适用于中小型规模）

这是最简单、最稳妥的方案。利用关系型数据库（如 MySQL）的事务特性和行级锁来保证原子性。

- **核心逻辑**：在更新库存时加上 `where inventory > 0` 条件。

- **SQL 示例**：

  ```SQL
  UPDATE stock SET count = count - 1 
  WHERE product_id = 101 AND count >= 1;
  ```

- **优点**：实现简单，不会出现超卖，完全依赖数据库事务保证一致性。

- **缺点**：在高并发下，大量请求竞争同一行的行锁，会导致数据库连接池耗尽，系统响应变慢。

------

## 方案二：分布式锁（适用于中等规模）

为了减轻数据库压力，可以在业务层拦截重复请求或串行化处理。

- **实现方式**：使用 **Redis (Redisson)** 或 **Zookeeper**。
- **流程**：
  1. 线程尝试获取针对 `product_id` 的分布式锁。
  2. 获取成功后，查询数据库库存。
  3. 判断库存充足，开启事务执行扣减。
  4. 释放锁。
- **缺点**：由于完全串行化，性能上限受限于锁的粒度。

------

## 方案三：Redis 预扣减 + 异步同步（高并发最佳实践）

这是目前大厂主流的抗流量方案，核心思想是将热点数据的扣减从数据库移到 Redis 中。

### 核心流程图

1. **库存同步**：活动开始前，将数据库库存加载到 Redis。

2. **Lua 脚本扣减**：使用 Redis Lua 脚本保证“查询 + 扣减”的原子性。

   ```Lua
   if (redis.call('exists', KEYS[1]) == 1) then
       local stock = tonumber(redis.call('get', KEYS[1]));
       if (stock > 0) then
           redis.call('incrby', KEYS[1], -1);
           return 1;
       end;
       return 0;
   end;
   return -1;
   ```
   
3. **发送消息队列 (MQ)**：Redis 扣减成功后，异步发送一条消息到 MQ。

4. **数据库最终一致性**：订单服务监听 MQ，异步创建订单并真正扣减数据库库存（或标记占用）。

------

## 关键问题处理

### 如何防止超卖？

- **数据库层面**：必须使用无符号整数或 `check (count >= 0)` 约束。
- **应用层面**：Redis 扣减逻辑必须保证原子性（Lua 脚本或 `decr` 返回值判断）。

### 如何处理“已下单未支付”的库存回收？

1. **设置订单超时时间**：利用 MQ 的延时队列（Delay Queue）。
2. **过期回滚**：
   - 用户取消订单或订单超时。
   - 发送回滚消息，将 Redis 库存加回去：`incr stock`。
   - 将数据库中的库存恢复。

### 扣减时机对比

| **时机**            | **优点**             | **缺点**                         |
| ------------------- | -------------------- | -------------------------------- |
| **下单即扣减**      | 实时性好，绝对不超卖 | 恶意下单占库存（“憋单”问题）     |
| **支付后扣减**      | 保证是有效订单       | 极易超卖（支付时才发现没货了）   |
| **预占库存 (推荐)** | 结合两者优点         | 下单扣减并保留一定时间，过期释放 |

------

## 架构演进建议

- **初始阶段**：直接使用 **MySQL 事务 + Optimistic Lock**（版本号机制）。
- **成长阶段**：引入 **Redis 缓存库存**，利用数据库作为兜底，增加 MQ 削峰。
- **极致阶段**：**分库分表** + **库存分段存储**（将一个商品的库存拆分到多个 Key 中，进一步分散锁竞争）。
