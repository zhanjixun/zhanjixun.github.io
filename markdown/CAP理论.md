# CAP理论

**CAP 理论**（CAP Theorem），又称布鲁尔定理（Brewer's Theorem），是分布式系统领域最核心的理论之一。

简单来说，它指出在一个分布式系统中，**一致性（Consistency）**、**可用性（Availability）**和**分区容错性（Partition Tolerance）**这三个特性，**不可能同时完全满足**。

------

### 1. CAP 的三个字母代表什么？

- **C - 一致性 (Consistency)**
  - **含义**：所有节点在同一时刻看到的数据都是一样的。
  - **表现**：你向系统中写入一个数据，接着无论从哪个节点读取，都必须能读到这个最新的数据。
- **A - 可用性 (Availability)**
  - **含义**：每个请求都能收到一个响应（无论成功或失败），且系统在任何时候都是可用的。
  - **表现**：系统不会因为某个节点故障或数据同步还没完成就拒绝服务。
- **P - 分区容错性 (Partition Tolerance)**
  - **含义**：当系统中某些节点之间的网络连接断开（出现“分区”）时，系统仍能继续运行。
  - **现实**：在分布式系统中，网络故障是必然会发生的。因此，**P 是必须要保证的**。

------

### 2. 为什么不能“三全其美”？

假设系统有两个节点 A 和 B，它们之间网络断了（发生了 **P**）：

1. 如果你要保证 **一致性（C）**：为了让 B 也能读到 A 更新后的数据，在网络恢复前，系统必须拒绝 B 的读取请求，这会导致系统不可用，即失去了 **可用性（A）**。
2. 如果你要保证 **可用性（A）**：B 节点继续响应用户的读取请求。但因为网络断了，B 没法收到 A 的最新更新，所以它返回的是旧数据，这就失去了 **一致性（C）**。

因此，在网络分区（P）发生时，你只能在 **C（保准）** 和 **A（保命）** 之间二选一。

------

### 3. 常见的组合与应用场景

由于分布式系统必须考虑网络故障，实际架构通常在 **CP** 或 **AP** 之间做权衡：

| **组合** | **特点**                                                     | **适用场景**                                               | **典型例子**                                   |
| -------- | ------------------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------- |
| **CP**   | 保证强一致性，牺牲可用性。如果网络出问题，系统宁愿报错也不给错数据。 | 金融交易、银行转账、分布式锁。                             | **Zookeeper**, **HBase**, **Redis (某些配置)** |
| **AP**   | 保证高可用，牺牲一致性。允许短时间内数据不一致（最终一致性）。 | 社交媒体（朋友圈点赞）、网页搜索、电商商品列表。           | **Cassandra**, **Eureka**, **DynamoDB**        |
| **CA**   | 保证一致性和可用性，牺牲分区容错。                           | **非分布式系统**（单机数据库）。在分布式环境下基本不存在。 | **MySQL (单机版)**                             |

------

### 4. 总结

CAP 理论并不是说我们要彻底放弃某一项，而是告诉我们：**在网络极端不稳定的情况下，系统必须有一个明确的优先级。** 现代互联网架构大多倾向于 **AP**，然后通过 **BASE 理论**（基本可用、软状态、最终一致性）来弥补数据一致性的延迟。
