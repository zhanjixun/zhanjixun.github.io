# Synchronized关键字

Java 的 `synchronized` 关键字是并发编程中元老级的角色。虽然现在有 `ReentrantLock` 等更灵活的工具，但 `synchronized` 在 JDK 1.6 经过大量优化后，性能已经非常出色，且因为使用简单（由 JVM 管理），依然是很多场景下的首选。

要“深入”理解它，我们需要从**用法、内存模型语义、底层原理（字节码与JVM）、以及锁升级机制**这几个维度来看。

------

### 1. 核心用法与锁对象

`synchronized` 的本质是**给对象加锁**。根据修饰的位置不同，锁住的对象也不同：

| **用法**         | **代码示例**                               | **锁住的对象**             | **作用范围**                          |
| ---------------- | ------------------------------------------ | -------------------------- | ------------------------------------- |
| **修饰实例方法** | `public synchronized void method()`        | **当前实例对象 (this)**    | 同一个对象实例的同步方法互斥          |
| **修饰静态方法** | `public static synchronized void method()` | **当前类的 Class 对象**    | 全局锁，所有该类的实例共享此锁        |
| **修饰代码块**   | `synchronized(obj) { ... }`                | **括号内指定的对象 (obj)** | 只有获取到 `obj` 的锁才能执行块内代码 |

> **注意**：如果是 `synchronized(this)`，它等同于修饰实例方法；如果是 `synchronized(ClassName.class)`，它等同于修饰静态方法。

------

### 2. 内存模型三大特性 (JMM)

`synchronized` 不仅保证了互斥执行，还完美解决了并发编程的三大问题：

1. 原子性 (Atomicity)：

   确保代码块内的操作作为一个整体执行，中间不会被打断。

2. **可见性 (Visibility)：**

   - **加锁前**：清空工作内存，强制从主内存读取最新变量值。
   - **解锁后**：必须将工作内存中的共享变量刷新回主内存。
   - 这也遵循了 happens-before 原则。

3. 有序性 (Ordering)：

   虽然它不禁止指令重排序，但由于“同一时刻只有一个线程执行”，单线程内的重排序不影响最终结果，从而在逻辑上保证了有序性。

------

### 3. 底层实现原理 (Deep Dive)

要深入理解，必须看它在 JVM 层面是如何实现的。

#### A. 字节码层面

如果你编译一段包含 `synchronized` 的代码并使用 `javap -c` 查看字节码：

- **代码块同步：** 使用 `monitorenter` 和 `monitorexit` 指令。
  - `monitorenter`：尝试获取对象的 Monitor（监视器锁）。
  - `monitorexit`：释放 Monitor。为了异常安全，编译器通常会生成两个 `monitorexit`（一个用于正常退出，一个用于异常退出）。
- **方法同步：** 字节码中没有特殊指令，而是在方法修饰符中设置了 `ACC_SYNCHRONIZED` 标志。JVM 调用方法时检查此标志，自动进行加锁和解锁。

#### B. 对象头 (Object Header) 与 Mark Word

Java 对象在内存中包含三部分：对象头、实例数据、对齐填充。锁的信息就存放在**对象头**的 **Mark Word** 中。

Mark Word 是一个动态的数据结构，根据锁状态的不同，存储的内容也不同（32位 JVM 下）：

- **无锁态：** 对象的 HashCode、分代年龄。
- **轻量级锁：** 指向栈中锁记录（Lock Record）的指针。
- **重量级锁：** 指向互斥量（Monitor）的指针。

#### C. 监视器锁 (Monitor)

当锁升级为重量级锁时，依赖的是操作系统底层的 Mutex Lock。在 HotSpot 虚拟机中，Monitor 是由 ObjectMonitor 实现的（C++）。

它主要包含：

- `_owner`：当前持有锁的线程。
- `_WaitSet`：调用 `wait()` 后进入等待状态的线程队列。
- `_EntryList`：等待获取锁（阻塞）的线程队列。

------

### 4. 锁升级与优化 (JDK 1.6+)

这是面试和深入理解的重中之重。在 JDK 1.6 之前，`synchronized` 是“重量级锁”，效率低（因为涉及用户态和内核态的切换）。后来引入了**锁升级**机制，锁的状态会根据竞争情况逐渐升级：

**无锁 $\rightarrow$ 偏向锁 $\rightarrow$ 轻量级锁 $\rightarrow$ 重量级锁**

#### 1. 偏向锁 (Biased Locking)

- **场景：** 只有一个线程访问同步块（实际上很多场景下锁是不存在竞争的）。
- **机制：** 当线程第一次访问锁时，将线程 ID 记录在对象头的 Mark Word 中。下次该线程再来，无需同步，直接进入。
- **撤销：** 一旦有第二个线程尝试获取锁，偏向模式结束。

#### 2. 轻量级锁 (Lightweight Locking)

- **场景：** 多个线程交替执行，或者竞争非常轻微（持有锁时间极短）。
- 机制： 1.  JVM 在当前线程的栈帧中建立一个 Lock Record。
  2. 将对象头的 Mark Word 拷贝到 Lock Record。
  3. 使用 CAS (Compare And Swap) 操作尝试将对象头的 Mark Word 指向 Lock Record。
  4. 如果成功，获取锁；如果失败，说明有竞争，进入自旋。

#### 3. 自旋锁 (Spin Lock)

- **机制：** 线程不立即阻塞（挂起），而是执行一个空循环（自旋），看看持有锁的线程是否很快释放。
- **优化：** 如果自旋多次（默认10次）还没拿到锁，或者是“适应性自旋”（JVM 根据上次自旋是否成功来决定这次自旋多久），则升级。

#### 4. 重量级锁 (Heavyweight Locking)

- **场景：** 竞争激烈，自旋失败。
- **机制：** 只有在这个阶段，才会真正调用操作系统的 Mutex Lock，挂起线程。这将导致**上下文切换 (Context Switch)**，开销很大。

------

### 5. Synchronized vs ReentrantLock

| **特性**     | **Synchronized**                  | **ReentrantLock**                                 |
| ------------ | --------------------------------- | ------------------------------------------------- |
| **实现层面** | JVM 层面 (内置关键字)             | JDK API 层面 (AQS 框架)                           |
| **使用方式** | 隐式加锁/解锁 (自动)              | 显式 `lock()` 和 `unlock()` (需在 finally 中释放) |
| **锁升级**   | 支持 (偏向/轻量/重量)             | 不支持 (基于 CAS 和 AQS)                          |
| **等待中断** | 不支持 (除非抛异常)               | 支持 `lockInterruptibly()`                        |
| **公平性**   | 非公平锁                          | 默认非公平，可选公平锁                            |
| **条件变量** | `wait()`/`notify()` (配合 Object) | `Condition` (支持多个条件队列)                    |

------

### 总结与建议

`synchronized` 已经不再是当年的“性能杀手”。它的优势在于：

1. **简单安全**：不会忘记释放锁导致死锁。
2. **自动优化**：JVM 会持续优化它（如锁消除、锁粗化）。
3. **够用**：对于大部分并非极度高并发的业务场景，它的性能完全足够。

**最佳实践：**

- 尽量缩小锁的粒度（只锁需要同步的代码块，而不是整个方法）。
- 不要在 `synchronized` 块中进行耗时的 IO 操作或网络请求（会阻止锁释放，导致其他线程长时间阻塞）。
- 如果在这个块中使用了 `String` 作为锁对象，请务必小心（因为字符串常量池的存在，可能导致意外的全局锁）。
