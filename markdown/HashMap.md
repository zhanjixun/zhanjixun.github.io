# HashMap

## 数据结构

HashMap使用存储键值对，数组的每个元素成为`桶`，当发生哈希冲突时（即不同的键计算的数组下标相同），HashMap将新插入的键值对挂在该位置的`链表`中(next)。在JDK8之后，当链表的长度超过阈值（默认8）时，链表会转换为 `红黑树`，以减少极端情况下的查询时间（从链表的O(n)优化为红黑树的O(log n)）。

> JDK 7 : `数组 + 链表`
>
> JDK 8 : `数组 + 链表 + 红黑树`，当链表长度超过8转换成红黑树，且数组长度≥64，则将链表转为红黑树。若数组长度 < 64，优先触发扩容（不树化）。

```java
// JDK中的Node定义（链表节点）
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;  // 指向下一个节点的指针
}
```

## 桶的定位

使用 `hashCode()` 获取键的哈希值，并通过 **扰动函数**（异或高16位）降低哈希冲突的可能性。

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

使用 `(n - 1) & hash` 确定键在数组中的索引（`n` 为数组长度，要求是 2 的幂）

## 哈希冲突

通常解决哈希冲突的办法有：

1. **拉链法**：这是一种非常常见的方法，简单理解就是把存在 hash 冲突 的 key，以单向链表的方式来存储，比如 HashMap 就是采用链式寻址法来实现的。
2. **再hash法**：就是当通过某个 hash 函数计算的 key 存在冲突时，再用另外一个 hash 函数对这个 key 做 hash，一直运算直到不再产生冲突。这种方式会增加计算时间，性能影响较大
3. **开放定址法**：也称为线性探测法，就是从发生冲突的那个位置开始，按照 一定的次序从 hash 表中找到一个空闲的位置，然后把发生冲突的元素存 入到这个空闲位置中。ThreadLocal 就用到了线性探测法来解决 hash 冲突的。

## 插入流程(put方法)

根据键的哈希值确定数组下标，分不同情况处理：

情况1：若桶为空，直接插入，创建新Node节点，存入数组对应索引位置。

情况2：桶不为空

1. 若当前节点的哈希值与新键的哈希值相同，且键的 `equals()` 返回 `true`，则**覆盖旧值**。否则，继续遍历后续节点。
2. 插入新节点：
   1. 链表：将新节点插入到链表，JDK 7为头插法，JDK 8改为尾插法，避免循环链表问题。此时会进行树化检查。
   2. 红黑树：调用红黑树的插入方法（`TreeNode.putTreeVal`）
3. 树化检查：
   1. 若链表长度超过 **8**，且数组长度 ≥ **64**，则将链表转为红黑树。
   2. 若数组长度 < **64**，优先触发扩容（不树化）。

## 扩容机制

触发条件：`size > threshold` 时触发扩容，其中`threshold = capacity * loadFactor`，扩容后会重新计算`threshold`。

JDK7 的扩容机制：扩容时候容量翻倍(`* 2`)，重新计算索引(**rehash**)，遍历旧数组(transfer方法)使用**头插法**将节点迁移到新数组，头插法可能会导致链表顺序反转，且在并发情况下可能会导致链表成环，后续get操作触发死循环。

JDK8中扩容时候容量仍是翻倍(`<<1`)，但不会对所有元素重新计算哈希值，而是通过 `hash & oldCap` 快速判断键值对是否需要移动：

- 若结果为 `0`：节点留在原索引位置。
- 若结果为 `1`：节点移动到 `原索引 + oldCap` 的位置。

这种方式减少了 hashCode 计算次数，提升了扩容效率。在迁移元素时候改为`尾插法`,避免链表成环(多线程下仍不安全，但不会导致死循环)。

问题：为什么扩容时节点重 hash 只可能分布在原索引位置或者 原索引长度+oldCap 位置呢？换句话说，扩容时使用节点的hash值跟oldCap进行位与运算，以此决定将节点分布到原索引位置或者原索引+oldCap位置上的原理是什么呢？

核心原理基于 **数组长度为2的幂** 以及 **位运算的高效性**。

这样设计的优势有：

1. **避免重新计算哈希**：
   直接通过 `hash & oldCap` 判断高位，无需重新计算整个哈希值。
2. **高效拆分链表**：
   链表中的节点只需按高位判断，即可快速分为两组（留在原桶或移动到新桶，同桶可以保持先后顺序）。
3. **时间复杂度优化**：
   单节点处理时间为 `O(1)`，整体扩容时间为 `O(n)`，但实际性能显著优于JDK7的重新哈希。

## 关键参数

| 参数                           | 说明                  | 取值                                                         |
| ------------------------------ | --------------------- | ------------------------------------------------------------ |
| DEFAULT_INITIAL_CAPACITY       | 默认初始容量          | 16                                                           |
| MAXIMUM_CAPACITY               | 最大容量              | 1 << 30                                                      |
| loadFactor/DEFAULT_LOAD_FACTOR | 负载因子/默认负载因子 | 0.75，是经验值，权衡空间占用和哈希冲突概率                   |
| TREEIFY_THRESHOLD              | 树化阈值              | 链表长度 `8`，退化阈值 `6`<br>基于泊松分布的统计结果（链表长度 ≥8 的概率极低） |
| size                           | 存放元素个数          |                                                              |
| capacity                       | 容量，数组的长度      | 默认为16，扩容翻倍                                           |
