# DDD - 领域驱动设计

**领域驱动设计**（Domain-Driven Design，简称 **DDD**）是一种软件开发的方法论，最初由 Eric Evans 在 2004 年提出。

简单来说，DDD 的核心思想是**让软件的复杂性与业务的复杂性相匹配**。它不再让技术细节（如数据库表结构、UI 界面）主导开发，而是让**业务概念**（订单、物流、支付逻辑）成为软件的核心。

它的本质是：**技术人员与业务专家联手，用同一套语言，把复杂的现实业务“翻译”成代码模型。**

------

### 1. 为什么我们需要 DDD？

在传统的开发模式（如“数据驱动设计”）中，我们往往先建数据库表，然后写 CRUD（增删改查）代码。

- **初期快**：业务简单时，这种方式效率极高。
- **后期痛**：随着业务越来越复杂，逻辑散落在各种 Service 和 SQL 中，代码变得难以理解和维护，改一个功能引发三个 Bug。

DDD 就是为了解决**“复杂业务逻辑难以维护”**这一痛点而生的。

------

### 2. DDD 的两大支柱

DDD 将设计分为两个层面：**宏观的战略设计**和**微观的战术设计**。

#### A. 战略设计 (Strategic Design) —— 宏观架构

这一层关注**“怎么切分系统”**以及**“怎么统一语言”**，主要解决大型系统的架构问题。

- 统一语言 (Ubiquitous Language)：

  开发人员和业务人员必须使用同一套术语。例如，业务方说“冻结账户”，代码里的方法名就应该是 freezeAccount()，而不是 updateStatus(0)。这消除了沟通中的翻译成本。

- 限界上下文 (Bounded Context)：

  这是 DDD 里的核心概念。它给业务概念划定了一个明确的边界。

  > **例子**：一个“商品”在**销售上下文**中关注的是价格和描述，而在**物流上下文**中关注的是重量和体积。DDD 建议不要建立一个巨大的“万能商品类”，而是在不同的上下文中建立不同的模型，互不干扰。

- 子域 (Subdomain)：

  将业务拆解为核心域（公司的核心竞争力）、支撑域（辅助功能，如防伪系统）和通用域（市面上可以直接买到的功能，如认证登录）。

#### B. 战术设计 (Tactical Design) —— 微观落地

这一层关注**“代码怎么写”**，即如何在具体的代码结构中落实领域模型。

| **概念**                      | **解释**                                                     | **例子**                                                     |
| ----------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **实体 (Entity)**             | 有唯一标识（ID）的对象，即使属性变了，它还是同一个对象。     | **用户 (User)**：修改了昵称，ID没变，还是这个用户。          |
| **值对象 (Value Object)**     | 没有ID，只通过属性值来区分的对象。                           | **地址 (Address)**：如果街道、城市都一样，就是同一个地址。   |
| **聚合 (Aggregate)**          | 一组相关对象的集合，就像一个“原子操作单元”，必须作为一个整体被修改。 | **订单 (Order)**：包含订单头和订单明细。删除订单时，明细也应一并删除。 |
| **聚合根 (Aggregate Root)**   | 聚合的入口。外部对象只能引用聚合根，不能直接修改聚合内部的细节。 | 你只能操作“订单”，不能直接操作“订单明细”。                   |
| **领域服务 (Domain Service)** | 无法归类到某个实体的跨对象业务逻辑。                         | **转账服务**：涉及两个账户实体的交互。                       |
| **领域事件 (Domain Event)**   | 业务中发生的有意义的事情，用于解耦。                         | “订单已支付”、“密码已修改”。                                 |

------

### 3. 贫血模型 vs. 充血模型

DDD 提倡**充血模型 (Rich Domain Model)**，这也是它与传统 MVC 开发最大的代码区别。

- **贫血模型 (传统的 MVC)**：
  - `User` 对象里只有 `get/set` 方法，没有逻辑。
  - 业务逻辑全在 `UserService` 里，例如 `userService.changePassword(userId, newPwd)`。
  - **缺点**：对象只是数据的载体，逻辑分散，不仅不仅面向对象，更像面向过程。
- **充血模型 (DDD)**：
  - `User` 对象里不仅有数据，还有行为。
  - 逻辑写在对象内部：`user.changePassword(newPwd)`。
  - **优点**：高内聚，对象对自己负责，业务逻辑清晰可见。

------

### 4. 什么时候该用 DDD？

DDD 不是银弹，它有很高的学习成本和复杂度成本。

- **✅ 适合场景**：
  - 业务逻辑非常复杂（如电商、金融、ERP、复杂的审批流）。
  - 业务变化快，需要代码结构灵活应对。
  - 团队中有能深入理解业务的领域专家。
  - 系统计划长期维护（3年以上）。
- **❌ 不适合场景**：
  - 简单的 CRUD 系统（如博客、简单的后台管理、小型外包项目）。
  - 注重性能到了极致（DDD 的分层和抽象可能会带来微小的性能损耗）。
  - 团队成员普遍经验不足，强行上 DDD 容易画虎不成反类犬。

### 总结

领域驱动设计（DDD）本质上是一种**治理复杂度的管理手段**。它通过**限界上下文**把大问题拆成小问题，通过**充血模型**把业务逻辑归还给对象本身，最终让代码变得像业务文档一样易读、易改。
