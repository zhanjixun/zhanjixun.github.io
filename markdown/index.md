### 异常处理执行顺序

```java
try {
    //代码1
    //异常
    return 表达式T;
} catch (Exception e) {
    //代码2
    return 表达式C;
} finally {
    //代码3
    return 表达式F;
}
```

正常情况：先try后finally

异常情况：先try执行到发生异常语句（发生异常后try后面的代码不执行），然后catch，然后finally

return的顺序：finally > catch (异常情况) 、finally > try (正常情况)

#### 为什么使用线程池

避免频繁地创建和销毁线程，达到线程对象的重用。

#### 线程池参数

| 参数              | 描述                                                         |
| ----------------- | ------------------------------------------------------------ |
| 核心线程数        | 线程池初始化的时候数量为0，当第一个任务到达时候创建corePoolSize个线程；核心线程永久存活，即使空闲也不会销毁。 |
| 最大线程数        | 当核心线程数已满，且工作队列也已存满，此时就会去判断当前线程数是否maximumPoolSize，如是则创建线程处理任务，如否则执行拒绝测量。 |
| 空闲超时时间/单位 | 如果当前线程数大于corePoolSize，且空闲线程超过keepAliveTime时间，则销毁线程。 |
| 工作队列          | 当核心线程已满，新提交的任务将放到工作队列中等待执行（前提是队列没满）。 |
| 创建线程的工厂    | 创建线程                                                     |
| 拒绝策略          | 线程数达到最大线程数，且工作队列已满，当提交新任务时候，则执行拒绝策略 |

#### 如何评估线程池的线程数量

**核心线程数**

CPU 密集型任务（如加密/解密、复杂算法、视频解码、压缩）：`核心线程数 ≈ CPU核心数 + 1`

> 为了提供CPU使用率并且减少不必要的切换

IO 密集型任务（如数据库查询、HTTP 请求、文件读写）：`核心线程数 ≈ CPU核心数 * 2 `

> 为了填补空缺，因为线程经常在休息（等待 IO）

**最大线程数**

若任务突发性强，可设置为 `核心线程数 * 2~3`，需避免过高导致线程竞争或内存溢出

**工作队列**

| 队列类型     | 队列实例              | 适用场景                                                     |
| ------------ | --------------------- | ------------------------------------------------------------ |
| 无界队列     | `LinkedBlockingQueue` | 适合任务量稳定且可控的场景，需警惕内存溢出OOM                |
| 有界队列     | `ArrayBlockingQueue`  | 限制队列长度，避免 OOM，适用于稳定的业务流量；               |
| 同步移交队列 | `SynchronousQueue`    | 任务不入队列，直接提交给线程池；适用于要求极低延迟、高吞吐量的场景（但可能造成任务丢失） |

**存活时间**

默认值：`60秒`（适合常规场景）

短任务场景可缩短（如10秒），长任务可延长

**拒绝策略**

| 拒绝策略            | 适用场景                                                     |
| ------------------- | ------------------------------------------------------------ |
| AbortPolicy（默认） | 直接抛出 RejectedExecutionException，适用于严格不允许丢任务的场景。 |
| CallerRunsPolicy    | 让提交任务的线程自己执行该任务，适用于降低任务提交速率。     |
| DiscardPolicy       | 直接丢弃任务，不抛异常（适用于不重要任务）。                 |
| DiscardOldestPolicy | 丢弃队列中最老的任务（适用于实时性高的任务）                 |

### ThreadLocal

每个 `Thread` 对象内部持有一个 `ThreadLocalMap`，用于存储该线程的所有 `ThreadLocal` 变量。其中Key为`ThreadLocal` 实例本身（弱引用，避免内存泄漏），Value是线程对应的变量副本。

#### 基本使用

```java
ThreadLocal<Object> threadLocal1 = new ThreadLocal<>();
for (int i = 0; i < 2; i++) {
    new Thread(() -> {
        try {
            threadLocal1.set(Thread.currentThread().getId() + "-1");
        	System.out.println(threadLocal1.get());
        } catch(Exception e) {
            
        } finally {
            threadLocal1.remove();
        }       
    }).start();
}
```

#### 如何解决哈希冲突

**开放地址法**：`ThreadLocalMap` 使用线性探测法（而非拉链法）解决哈希冲突。

**魔数哈希**：通过 `0x61c88647`（斐波那契散列）计算索引，均匀分布键值对，减少冲突概率。

#### 内存泄漏问题

`ThreadLocalMap`的Key为弱引用，一旦满足了“GC Roots 不可达”这个条件，下一次GC时，Key引用的ThreadLocal对象会被回收，导致这个Entry里的key字段变成null。而value是强引用，不会被回收，就会导致内存泄漏。所以当前线程使用完ThreadLocal 后需要手动`remove()`。

### 垃圾回收

#### 如何确定哪些对象可以回收

**引用计数法**

>给对象添加引用计数器,有引用加1；引用失效时减‎1;引用数为0时代表对象不可能再被使用。
>
>缺点：无法解决循环引用问题

**可达性分析法**

> 以GC Roots作为起点,向下搜索,走过路径成为引用链.当对象到GC Roots没有任何相连时,则该对象是不可用的。

哪些对象可以作为GC Roots：

1. 虚拟机栈中引用的对象
2. 方法区中类静态属性引用的对象
3. 方法区中常量引用的对象
4. 本地方法栈中JNI引用的对象
5. JVM 内部的引用
6. 被同步锁 synchronized 持有的对象

#### 垃圾回收算法

| 算法          | 原理                                                         | 优点                                                         | 缺点                                                         |
| :------------ | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **标记-清除** | 1. **标记阶段**：遍历所有根对象（GC Roots），递归标记所有可达对象。 2. **清除阶段**：线性堆内存，回收未被标记对象的内存空间。 | 1. 实现简单，逻辑清晰 2. 无需移动对象，适合大对象或老年代    | 1. **内存碎片**：产生大量不连续内存，导致大对象无法分配，提前触发GC 2. **效率低**：两次遍历耗时，STW时间较长 |
| **标记-复制** | 1. 内存划分为大小相等的两块（From和To）。 2. 仅使用一块（From），存活对象复制到另一块（To）。 3. 清空原块，交换角色。 | 1. **无碎片**：内存规整，分配简单高效（指针碰撞） 2. **吞吐量高**：适合存活对象少的场景（如新生代） | 1. **内存利用率低**：始终有一半空间闲置 2. **复制开销**：存活对象多时效率差（适合新生代） |
| **标记-整理** | 1. **标记阶段**：同标记-清除。 2. **整理阶段**：将存活对象向一端移动，然后清理边界外内存。 | 1. **无碎片**：内存规整，避免大对象分配失败 2. **空间利用率高**：无需额外预留空间 | 1. **开销较大**：需要移动对象并更新引用，STW时间长 2. **复杂度高**：需处理跨页引用、内存重映射等 |
| **分代收集**  | 结合上述算法： - **新生代**：标记-复制（存活对象少） - **老年代**：标记-清除/整理（存活对象多） 配合卡表、写屏障等优化。 | 1. **综合性能最优**：对不同生命周期对象采用最适算法 2. **吞吐量高**：新生代快速回收，老年代减少GC频率 | 1. **实现复杂**：需维护跨代引用、分代边界 2. **参数调优难**：分代大小、晋升阈值等需精细调整 |

### 事务

#### 四大特性

事务的四大特性ACID：`原子性`、`一致性`、`隔离性`和`持久性`

| 特性   | 描述                                                         |
| ------ | ------------------------------------------------------------ |
| 原子性 | 事务是一个原子操作单元，对数据的修改要么全部执行，要么全部不执行 |
| 一致性 | 事务在开始和完成时，数据必须保持一致状态                     |
| 隔离性 | 事务之间应该隔离开来，使每个并发中的事务不会互相干扰         |
| 持久性 | 事务完成后，对数据的修改是永久的，即使系统发生故障也能保持   |

#### 并发带来的问题

| 问题       | 描述                                                         |
| ---------- | ------------------------------------------------------------ |
| 脏读       | 一个事务读取到另一个事务未提交的数据                         |
| 不可重复读 | 一个事务对同一行数据重复读取两次，但得到的结果不同           |
| 幻读       | 一个事务执行两次查询，但第二次查询的结果包含了第一次查询中未出现的数据 |
| 丢失更新   | 多个事务同时更新一行数据，后提交（或撤销）的事务将之前事务提交的数据覆盖了 |

#### 事务隔离级别

| 隔离级别 | 英文名称         | 描述                                                         | 脏读   | 不可重复读 | 幻读   |
| -------- | ---------------- | ------------------------------------------------------------ | ------ | ---------- | ------ |
| 读未提交 | Read Uncommitted | 事务可以读取其他事务未提交的更改                             | 可能   | 可能       | 可能   |
| 读已提交 | Read Committed   | 事务只能读取其他事务已提交的数据                             | 不可能 | 可能       | 可能   |
| 可重复读 | Repeatable Read  | 事务内多次读取同一数据的结果一致，不可以读取其他事务已提交的数据 | 不可能 | 不可能     | 可能   |
| 串行化   | Serializable     | 事务完全串行执行                                             | 不可能 | 不可能     | 不可能 |

注意：丢失更新是很严重的情况，无论哪种隔离级别都不允许发生丢失更新。MySQL默认的隔离级别是`可重复读`

一般来说，事务的隔离级别越高，越能保证数据库的完整性和一致性，但相对来说，隔离级别越高，对并发性能的影响也越大。

因此，通常将数据库的隔离级别设置为`读已提交`，它既能防止脏读，又能有较好的并发性能。虽然这种隔离级别会导致不可重复读、幻读和第二类丢失更新这些并发问题，但可通过在应用程序中采用悲观锁和乐观锁加以控制。

#### 如何解决循环依赖

简单来说就是通过`三级缓存`提前暴露未初始化的Bean实例来解决循环依赖。

依赖注入方式有：1、字段注入 2、 Setter 注入 3、构造器注入

Bean的作用域范围有：1、单例（Singleton） 2、原型（Prototype）

Spring无法解决原型作用域或构造器注入的循环依赖

1. **创建 Bean A**：
   - Spring 实例化 Bean A（调用构造器），此时 A 对象是“半成品”（未填充属性）。
   - 将 A 的早期引用（未初始化的对象）存入 **三级缓存（SingletonFactories）**。
2. **填充 Bean A 的属性**：
   - Spring 发现 Bean A 依赖 Bean B，尝试从容器中获取 B。
3. **创建 Bean B**：
   - Spring 实例化 Bean B（调用构造器），此时 B 对象是“半成品”。
   - 将 B 的早期引用存入三级缓存。
4. **填充 Bean B 的属性**：
   - Spring 发现 Bean B 依赖 Bean A，尝试从容器中获取 A。
   - **从三级缓存中获取 A 的早期引用**，注入到 B 中，完成 B 的初始化。
   - 将初始化后的 Bean B 放入 **一级缓存（SingletonObjects）**。
5. **完成 Bean A 的初始化**：
   - Bean B 创建完成后，将 B 注入到 A 中，完成 A 的初始化。
   - 将初始化后的 Bean A 放入一级缓存。

#### 事务失效场景

| 场景                       | 描述                                                         |
| -------------------------- | ------------------------------------------------------------ |
| 事务方法的访问修饰符不当   | **场景描述：**如果在 Spring 中，事务方法被声明为 `private`、`final` 或 `static`，则事务可能不会生效。这是因为 Spring 使用代理机制来管理事务，而这些修饰符会影响代理的生成。spring 要求被代理方法必须是`public`的，在`AbstractFallbackTransactionAttributeSource`类的`computeTransactionAttribute`方法中有个判断，如果目标方法不是 `public`，则`TransactionAttribute`返回 null，即不支持事务。<br>**解决方案：**将事务方法声明为 `public`，避免使用 `private`、`final` 或 `static` 修饰符。 |
| 方法内部调用自身的事务方法 | **场景描述：**在同一个类中，方法内部调用另一个带有 `@Transactional` 注解的方法时，事务可能不会生效。这是因为 Spring 的事务管理依赖于 AOP 代理机制来实现事务的控制。当一个方法内部直接调用同一类中的另一个方法时，调用的是当前对象的实例方法，而不是通过代理对象进行调用。由于事务管理是通过代理对象的切面实现的，直接调用会导致事务增强失效，事务无法生效。<br>**解决方案：**为了解决同一类中方法内部调用导致事务失效的问题，可以考虑以下几种解决方案：使用 `AopContext.currentProxy()` 获取代理对象、使用 `ApplicationContext` 获取代理对象、将事务方法提取到另一个服务类中 |
| 异常被捕获但未重新抛出     |                                                              |
| 使用了错误的事务传播行为   |                                                              |
| 异步方法中的事务失效       |                                                              |
| 数据库不支持事务           |                                                              |

### 缓存穿透和缓存雪崩是什么，怎么解决？

**缓存穿透**

> 缓存穿透，即请求缓存中不存在的数据，导致所有的请求都打到数据库上，从而数据库连接异常。
>
> 解决方案：①布隆过滤器  ②缓存空值

**缓存雪崩**

> 缓存雪崩，即缓存`同一时间大面积失效`，这个时候又来了一波请求，结果请求都打到数据库上，从而导致数据库连接异常。
>
> 解决方案：给缓存的失效时间，加上一个随机值，避免集体失效。

### Redis的过期策略和内存淘汰机制

Redis采用`定期删除`+`惰性删除`的过期策略。

①定期删除：默认100ms去*随机抽取*设置了过期时间的数据，如已过期则删除。

②惰性删除：当redis去获取一个数据的时候，检查是否已经过期，如过期则删除。

### 如何解决Redis双写一致性问题

**先更新数据库，再删除缓存。**如果要求强一致性，可以是读写锁。

存在删除缓存失败的情况，需要提供补偿机制（如消息队列）。

存在并发线程将旧数据写回缓存的情况，可以采用`延迟双删方`案。

#### 使用Redisson

1. **可重入性**：使用Redis中Hash结构记录重入次数，根据计数器释放锁，类似 `ReentrantLock`
2. **自动续约（Watchdog）**：定期检查锁是否被业务线程持有，如果持有，则自动延长锁的过期时间

4. **多种锁类型**：可重入独占锁、读写锁、公平锁、分布式信号量、分布式倒计时锁
5. **异步和阻塞调用**：`tryLockAsync()`、`lockAsync()` 支持异步操作；可以直接指定超时和等待时间
6. **可靠性**：内置 Lua 脚本保证原子性

### 分布式事务

#### 两阶段

通过一个协调者统一管理所有参与者的事务提交或回滚。

- **阶段1（准备阶段）**：协调者询问所有参与者是否准备好提交事务。
- **阶段2（提交/回滚阶段）**：所有参与者响应“同意”后，协调者发送提交命令；否则回滚。

#### TCC

业务代码中显式定义事务的补偿逻辑，分三个阶段：

- **Try**：预留资源（如冻结库存）。
- **Confirm**：确认操作（如扣减冻结的库存）。
- **Cancel**：取消操作（如释放冻结的库存）。
