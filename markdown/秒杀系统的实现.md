# 秒杀系统的实现

设计秒杀系统（Flash Sale）的核心挑战在于**极高并发下的瞬时流量峰值**。如果设计不当，巨大的流量会直接压垮数据库，甚至导致整个系统雪崩。

设计秒杀系统应遵循原则：**流量削峰、先验后扣、读写分离、防止超卖。**

------

## 整体架构设计：分层过滤

秒杀系统的设计就像一个漏斗，从上到下逐层拦截无效流量，最后只让极少数的请求到达数据库。

### ① 接入层（CDN & Nginx）

- **动静分离**：将秒杀页面的 HTML、JS、CSS、商品图片等静态资源全部缓存到 CDN。
- **限流降级**：在 Nginx 层配置 IP 限流，防止恶意爬虫脚本疯狂刷新。

### ② 应用层（业务服务）

- **接口隐藏**：秒杀开始前，接口地址是随机生成的动态 URL，防止用户通过脚本提前抢购。
- **本地缓存**：在 JVM 内存中缓存秒杀活动标记（例如 `isStarted = false`），减少对 Redis 的请求。

### ③ 缓存层（Redis）

- **库存预热**：活动开始前，将库存数据加载到 Redis 中。
- **原子扣减**：利用 **Lua 脚本** 判断并扣减库存，保证“查询+扣减”的原子性，彻底杜绝超卖。

------

## 核心流程：秒杀三部曲

### 第一步：Redis 预扣库存

不要直接查数据库。所有请求先在 Redis 中进行库存扣减。

- 如果 Redis 返回库存不足，直接给用户返回“已售罄”。
- 如果扣减成功，进入下一步。

### 第二步：消息队列（MQ）削峰

扣减成功后，不直接操作数据库生成订单，而是向 MQ（如 RocketMQ 或 RabbitMQ）发送一条异步消息。

- **作用**：将瞬时的高并发请求转变为顺序的平滑流，保护后端数据库。

### 第三步：数据库订单处理

订单服务异步消费 MQ 消息：

1. 开启数据库事务。
2. 生成订单记录。
3. **最终库存扣减**：同步数据库中的库存字段。
4. 发送支付提醒给用户。

------

## 关键技术难点及应对方案

### A. 防止超卖

- **数据库兜底**：更新 SQL 必须带条件：`UPDATE stock SET nums = nums - 1 WHERE id = ? AND nums > 0`。
- **唯一索引**：在订单表建立 `user_id` 和 `activity_id` 的联合唯一索引，防止同一个用户抢到两份。

### B. 解决“库存遗留”问题

如果用户下单了但未支付，库存被占用了怎么办？

- **延迟队列**：下单时发送一个 15 分钟的延迟消息。
- **自动释放**：如果 15 分钟后订单未支付，系统自动关闭订单，并调用 Redis 的 `INCR` 命令回滚库存。

### C. 数据库性能优化

- **热点行竞争**：如果秒杀单品极其火爆，数据库单行更新会由于行锁导致排队。
- **分段库存**：将 1000 个库存拆分到 10个 Key 中（stock_1, stock_2...），让请求分散到不同的存储分片，提升并发上限。

------

## 安全与防作弊

1. **验证码机制**：在点击“秒杀”按钮前，弹出复杂的图形验证码，拉长请求时间，有效防止机器脚本。
2. **黑名单限制**：对短时间内高频请求的 UID 或 IP 进行动态封禁。
3. **风控系统**：接入风控引擎，识别是否为模拟器或群控设备。

------

## 总结：系统演进路径

| **阶段**   | **核心组件**                       | **支撑并发量**     |
| ---------- | ---------------------------------- | ------------------ |
| **基础版** | 数据库行锁 + 简单缓存              | 100 ~ 500 TPS      |
| **进阶版** | Redis Lua + 异步 MQ                | 5,000 ~ 20,000 TPS |
| **终极版** | 负载均衡 + 静态化 + 容器化水平扩展 | 100,000+ TPS       |

> 解决方案：重新设计静态化的商品页面，使前端页面刷新不需要经过应用服务器。

**突然增加的网络及服务器带宽问题**

> 解决方案：增加网络带宽，使用`动静分离`，将商品页面缓存在`CDN`中。

**防止破解和提前下单**

> 解决方案：`隐藏秒杀URL`或者将URL动态化，只有在秒杀开始时才能得到。
